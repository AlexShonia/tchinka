# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"El Tchinko": a multiplayer wave-survival game. Server-authoritative Node.js game loop, three.js browser client, talking over WebSockets. Plain JS (ES modules, no TypeScript). No tests or linter are configured.

## Commands

- `npm run server`: start the Node server (HTTP + WebSocket on port 1234). It serves the **built** client from `dist/`.
- `npm run client`: Vite dev server for the client (hot reload). The client connects to `ws://<hostname>:1234`, so the game server must also be running.
- `npm run build`: build the client into `dist/` (committed to git). Rebuild before expecting `localhost:1234` to reflect client changes.

## Architecture

Three code areas under `src/`: `server/`, `client/`, `shared/`. Both sides use a Receiver/Sender/Service layout: Receiver parses incoming messages, Service applies them, Sender emits outgoing ones.

**Server (`src/server`)**
- `server.js` wires everything. `outgoing/Sender.js` owns the game loop: a `setInterval` calls `gametick/tick.js` and then broadcasts a full state snapshot as JSON to all clients, every tick.
- `shared/combatConfig.js` holds `TICK_MS` and all combat timing/damage numbers. Timings are measured in **ticks**, not ms. Note that `Sender.js` has its own `TICK_RATE = 20` constant that duplicates `TICK_MS`.
- `common/GameData.js` is the world state (players map, enemies array, wave, id counters).
- Entities: `Entity` (x, z) → `Alive` (health, moveSpeed, `combatState`) → `Player` / `Enemy`. Combat goes through `Alive`: `canAttack(target)` (overridden per class by `instanceof`, so no PvP), `takeDamage(amount)` (moves the target to `dead`), and `gameData.findAlive(id)`. `tick.js` removes dead enemies after all entities tick.

**State machine (the core pattern)**
- Every `Alive` has `combatState = { state: "<name>", states: { name: StateInstance }, transitions: { name: { event: nextName } } }`. `currentState` returns the active instance. Each state is constructed with its owning actor (`new IdleState(this)`), so ticks and requests don't pass the actor.
- States live in `server/gametick/states/` and extend `BaseState(actor, name)`: `initialize(context)`, `tick(gameData)`, `passiveTick()`. State names are the `State` enum (`gametick/State.js`), never raw strings.
- **Transitions are a per-entity map, never hardcoded in a state.** A state reports what happened via `actor.transition(Event.X, context)` (the `Event` enum, `gametick/Event.js`, grouped by who emits each event); the actor looks up `combatState.transitions[currentState][event]` (`gametick/transitions/PlayerTransitions.js`, `EnemyTransitions.js`), calls `nextState.initialize(context)` (one named context object like `{ targetId }` or `{ moveTarget }`, destructured by each state) and switches. An event with no entry in the current state's row is ignored. Client requests (`Service`) are just events too (`MOVE_REQUESTED`, `ATTACK_REQUESTED`), so states have no request handlers. To change behavior, edit the map; to give an entity new behavior, give it a different map. Players and enemies differ by their states and maps, not by hooks: players wait in `IdleState` (no tick), enemies start in `SeekTargetState` (finds the nearest target, emits `TARGET_FOUND`). Dying is the one global exception: `takeDamage` calls `changeState(State.DEAD)` directly.
- Entity policy lives on `Alive` hooks: `canAttack(target)` (overridden by `instanceof`, so no PvP), `takeDamage(amount)`; plus `gameData.findAlive(id)`. `tick.js` removes dead enemies after all entities tick.
- `passiveTick()` runs on **every** state every tick, even inactive ones, and only touches state-local data (e.g. cooldown/recovery timers), never `gameData` or other actors. `tick(gameData)` runs only on the current state. See the comment in `BaseState.js`.
- An attack is one state with an internal phase, not several states: `BasicAttackState` (`State.BASIC_ATTACK`: windup → hit, damage lands when the hit begins → recovery) and `JumpAttackState` (`JUMP_ATTACK`: windup → air → recovery). `BasicAttackState.recoveryTimer` is the attack cooldown: it starts with the hit (`startCooldown`, covering hit + recovery, also called by the jump), `passiveTick` counts it down even while the actor is in another state, recovery lasts until it is 0, and `actor.isAttackOnCooldown` exposes it. If targeting reaches range while it is still running, the attack state is entered already in recovery and just waits it out (then `ATTACK_FINISHED` → targeting → a fresh attack). What the client is told is `state.visualState` (the state name, but `idle` for the whole recovery phase, so nothing is drawn as an attack while you wait out the cooldown), sent by `Sender`.
- Abilities: the client sends `{ type: "ability", key: "q" }`; `Service.useAbility` maps the key to an `AbilityName` and `Player.useAbility` sets `combatState.abilities[name].armed` (ignored while that ability's own cooldown runs). `BasicAttackState.tick` checks `actor.hasArmedAbility` in every phase and emits `ABILITY_ARMED`, which the player map routes to `JUMP_ATTACK`, so Q cuts in immediately and doesn't wait for the attack cooldown. The jump follows the same transition rules as the basic attack, except in its `air` phase, where `MOVE_REQUESTED` is ignored (a `subState(State.JUMP_ATTACK, JumpAttackPhase.AIR)` row in the map; phase rows win over the state row and `null` means ignored, see `transitions/types/SubState.js`). The ability is spent (disarmed + `JumpAttackState.cooldownTimer` started, counted in `passiveTick`, separate from the attack cooldown) only if the landing actually damaged someone. `Sender` sends `abilities` per player (armed + cooldown ticks) for the HUD slot and the armed tint. Numbers in `PLAYER_JUMP` are placeholders.
- More abilities (W/E/R), each its own state, started by an ability `event` instead of arming (`Player.useAbility` pays mana only if `transition` returned true): `ShoulderChargeState` (W, `DASH_REQUESTED`: windup → rush → bump + knockback → recovery), `SpinAttackState` (E, `SPIN_REQUESTED`: 150 ticks of per-tick area damage; `MOVE_REQUESTED` maps back to the same state, whose `initialize` then only swaps `moveTarget` and keeps the timer), `ShieldThrowState` (R, `SHIELD_REQUESTED`: shield bounces between random enemies in range, then returns; its `shield` position is sent in the snapshot). These have no rows for move/attack in `PlayerTransitions`, only `ABILITY_FINISHED` → idle, so the player can't interrupt them. Numbers in `PLAYER_CHARGE/SPIN/SHIELD` are placeholders.
- Convention: all transient state-machine fields (targets, timers, `isMoving`, etc.) live in `entity.combatState`, **never** as flat properties on `Player`/`Enemy`. Entity classes hold only identity and physics. Apply this to any new entity type too.
- Timers are currently in flux. The most recent commit says they are not settled, so expect refactors in this area.

**Client (`src/client`)**
- `client.js` sets up three.js, then runs the render loop: flush the outbox, update the camera, run input, tick views, render.
- Incoming: `incoming/Receiver.js` → `GameStateService` applies `welcome`/`state` messages by syncing server entities to view objects (`common/view/types/*View.js`), creating and removing them by id. The client keeps no game logic and just renders what the server says.
- Outgoing: input (`outgoing/input/`) → `Service` queues commands in an outbox → `Sender.flush` sends them over the WebSocket.
- Client-side `common/view/states/` has one animation per attack (`BasicAttackState`, `JumpAttackState`) covering only the active part (windup + hit, windup + air); it holds its end pose until the server reports idle (recovery), and then the view eases the pose back to rest (`common/view/settle.js`; the jump's squash is eased by the view too). Phase durations come from `combatConfig`. Regular attacks swing around the y axis (`userData.swingYaw` added to the facing yaw: turn right, swing left), only the Q jump pitches (`rotation.x`, euler order `YXZ`, so the pitch is relative to the facing). The server keeps `Entity.facing` (yaw, set via `Alive.faceTowards(point)` and sent in every snapshot) and the views turn toward it (`common/view/facing.js`).
